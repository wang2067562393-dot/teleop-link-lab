# 🎮 teleop-link-lab · 遥操作链路实验台

> 控制端 → 弱网代理 → 模拟机器人 → 视频回流，全链路打点。
> 目标不是「做一个遥操作系统」，而是回答三个现场问题：**延迟多少？问题在哪一段？该降级还是该修？**

## 为什么做这个

遥操作出问题时，最常见的两种反应都不对：

- 「卡了」→ 重启整套链路。问题没定位，下次还会卡；
- 「延迟高」→ 降分辨率。但如果延迟来自链路而不是带宽，降画质一点用都没有（下面的实验会证明这一点）。

这个仓库把链路拆成可测量的四段，每一段都能单独注入故障、单独看数字，然后才谈修和降级。

## 30 秒看懂

| 我测了什么 | 结果 |
|---|---|
| 本机回环基线 | 指令往返 **0.4–0.9 ms**（p50，随 CPU/调度浮动，不跨机器可比），画面端到端 **0.5–0.7 ms**（p95） |
| 注入 100 ms 单向延迟 | 往返 **203.8 ms**，画面 **110.0 ms** —— 与注入值一致，说明注入器可信 |
| 注入 5% 丢包 | 指令延迟几乎不变，但**丢帧率从 1.7% 升到 8.3%** —— 丢包伤的是画面，不是指令 |
| 200 ms + 10% 丢包 | 降级触发 2 次到 L2，码率从 496 kbps 降到 155 kbps，**但延迟一点没降** |

**结论：延迟高的时候降画质是错的直觉。** 降级省的是带宽，救不了延迟；延迟必须回到链路上修。

## 完整实验结果

`python -m teleoplab suite`（6 场景 × 6 秒，固定种子，单机回环）：

| 场景 | 注入 | 指令年龄 p50 | p95 | p99 | 抖动 | 画面 p95 | 丢帧率 | 下行码率 | 末级画质 | 切换 |
|---|---|---|---|---|---|---|---|---|---|---|
| baseline | 0ms | 0.4 | 0.6 | 0.7 | 0.1 | 0.5 | 0.0% | 496 | L0 (20fps 64x48) | 0 |
| delay-100ms | 100ms | 203.8 | 213.2 | 223.6 | 3.1 | 110.0 | 1.7% | 496 | L0 (20fps 64x48) | 0 |
| delay-100ms+loss-5% | 100ms / 5%丢 | 204.4 | 215.5 | 223.7 | 4.0 | 109.9 | 8.3% | 496 | L0 (20fps 64x48) | 0 |
| delay-200ms+jitter-20ms+loss-10% | 200ms±20 / 10%丢 | 405.6 | 428.1 | 437.9 | 15.3 | 218.8 | 6.8% | 155 | L2 (5fps 16x12) | 2 |
| delay-300ms-无降级 | 300ms | 607.1 | 614.8 | 616.3 | 3.3 | 311.1 | 6.7% | 496 | L0 (20fps 64x48) | 0 |
| delay-300ms-有降级 | 300ms | 606.3 | 614.3 | 615.9 | 3.5 | 309.3 | 9.8% | 167 | L2 (5fps 16x12) | 2 |

口径（每个数字都能复算）：

- **指令年龄** = 控制端发出指令 → 收到机器人立即回传的 ack 的时间差，含双向网络与机器人处理；
- **画面端到端** = 机器人采集帧 → 控制端收到帧；
- **抖动** = 相邻两次指令年龄的绝对差均值（不是标准差）；
- **下行码率** = 发出帧总字节 × 8 / 时长（v0.1 是原始像素，未压缩）。

## 跨机器复现（2026-11-21）

在**另一台机器**上重跑同一 commit，验证哪些结论是机器无关的、哪些是本机噪声。

- 原机：Windows 11 + 未知型号（`reports/weaknet.json` 入库时的机器）
- 复现机：AMD R5-5600 / Windows 11 10.0.26300 / Python 3.12.10

复现命令：`python -m teleoplab suite`，将输出的 `weaknet.json` 与 `reports/weaknet.json` 逐项对比。

### 可复现（偏差 ≤ 5%）

| 场景 | 指标 | 入库值 | 复现机 | 偏差 |
|---|---|---|---|---|
| delay-100ms | 指令 p50 | 203.75 ms | 202.75 ms | **-0.5%** |
| delay-100ms | 指令 p95 | 213.22 ms | 208.07 ms | -2.4% |
| delay-100ms | 画面 p95 | 109.96 ms | 104.20 ms | -5.2% |
| delay-200ms+jitter-20ms+loss-10% | 指令 p50 | 405.64 ms | 401.91 ms | -0.9% |
| 全部场景 | 下行码率 | 495.68 / 154.62 / 166.72 kbps | 完全一致 | **0.0%** |

**注入值可复现、码率可复现、降级不降延迟可复现** —— 这三条是结构性的，换机器不变。

### 不可复现（已在局限中标注口径）

| 指标 | 入库值 | 复现机 | 偏差 | 原因 |
|---|---|---|---|---|
| baseline 指令 p50 | 0.399 ms | 0.550 ms | +37.7% | 亚毫秒回环延迟由 OS 调度与 CPU 决定 |
| baseline 画面 p95 | 0.473 ms | 0.742 ms | +56.7% | 同上，绝对差仅 0.27 ms |
| 各注入场景抖动 | 3.1–3.5 ms | 1.5–1.6 ms | -49% ~ -55% | 抖动测的是本机调度噪声下界，机器间差约 2× |

**结论：基线延迟与抖动应读作「本机量级」，不要当成绝对值引用。** 需要跨机器比较时，
用「注入值 vs 实测值」的相对关系，或用码率这类与调度无关的量。

## 架构

```
 operator.py ──cmd(seq, ts)──▶ ┌──────────────┐ ──▶ robot_sim.py
     ▲                         │ netem_proxy  │         │ 100 Hz 固定步长
     │                         │ 延迟/抖动/丢包 │         │
     │ ◀──state(ack, ts)─────── │ 独立线程排程   │ ◀───────┘
     │                         └──────────────┘
     │ ◀──frame(id, ts)─────────────────────── 合成画面（按等级改帧率与分辨率）
     │
     └─▶ policy.py：p95 > 250ms 降档（带回滞）→ ctrl(level) → 机器人
```

三个设计决定，都是被坑出来的：

1. **代理夹在中间，所有包必须真过它**。否则测的是本机回环，不是链路。
2. **时间戳在采集点打，用 `perf_counter_ns`**。不用 `time.time()`，也不用发送点补。
3. **延迟注入用独立线程排程**，不用 `asyncio` 定时器（原因见下面的调试记录）。

## 跨机器模式

单机回环是最大的一条局限。现在可以拆成三个进程跑，跨机器用：

```bash
# 机器 A（机器人端）
python -m teleoplab serve --role robot --port 9100 --duration 40

# 机器 B（代理，可选；放在第三台机器上最接近真实弱网）
python -m teleoplab serve --role proxy --listen-port 9000 \
    --robot 192.168.1.5:9100 --delay-ms 50 --duration 35

# 机器 C（控制端）
python -m teleoplab serve --role operator \
    --proxy 192.168.1.6:9000 --duration 20 --out reports/remote.json
```

### 时钟怎么对齐

跨机器第一件事是**别信时间戳**：两端的 `perf_counter_ns()` 起点不同、还会各自漂移。但只有一半的指标受影响：

| 指标 | 是否依赖跨机器时钟 | 原因 |
|---|---|---|
| 指令往返（cmd_age） | **不依赖** | 发送 `t0` 与收到 `t2` 都在控制端时钟上，差值就是往返 |
| 画面端到端 | 依赖 | 采集时间戳由机器人打，必须先换算 |

换算用不新增报文的办法：机器人收到指令会立即回带自己时间戳的 `state`，于是

```
offset_i = ts_robot - (t0 + t2) / 2
```

单程不对称会让每个样本带误差（上下行差 `d` 则误差约 `d/2`），所以取 **RTT 最小** 的样本
而不是平均——平均会被抖动放大。实现见 `teleoplab/remote.py` 的 `OffsetEstimator`。

### 本机验证结果（192.168.3.117，走真实网卡）

| 指标 | 注入 | 实测 |
|---|---|---|
| 指令往返 p50 | 50 ms 单向 | **101.88 ms** |
| 指令往返 p95 | 同上 | 102.90 ms |
| 抖动 | — | 0.70 ms |
| 时钟偏移估计 | — | **0.028 ms**（481 样本，最小 RTT 100.5 ms） |
| 画面端到端（校正后） | — | 51.67 ms |

同机两进程走 LAN 地址，偏移估计误差 0.03 ms —— 说明算法本身没错。
**真实双机（不同主机、Wi-Fi）还没跑过**，这是下一步要补的数字。

## 调试记录

这个仓库里最有价值的部分可能不是代码，而是这三个「一开始数字是错的」的过程。

### ① 基线 30.6 ms：Windows 定时器把 10 ms 的 tick 拖成 15.6 ms

第一次跑基线，零网络延迟下指令年龄 p50 = **30.6 ms**，抖动 25.2 ms，分布双峰。
逐段排除后确认：`asyncio.sleep` 在 Windows 上受 15.6 ms 定时器粒度限制，100 Hz 循环
持续落后再追赶，产生突发。

处理：`timeBeginPeriod(1)` 提高进程定时器分辨率 + 最后 3 ms 改自旋等待。
基线降到 16.1 ms、抖动 1.9 ms —— 但仍然是 16 ms，说明还有别的原因。

### ② 基线还是 16 ms：`loop.time()` 的分辨率就是 15.6 ms

微基准（120 次 100 Hz 循环）显示：裸 `asyncio.sleep` 与「高分辨率 + 自旋」的 p50 都是 15.00 ms。
Windows 上 `loop.time()` 来自 `GetTickCount64`，分辨率约 15.6 ms，**事件循环本身做不到 10 ms 精度**。

处理：不再用「等下一个 tick 再回状态」来测延迟，改成**收到指令立即回 ack**。
基线降到 **0.4 ms** —— 因为这时测到的才是链路本身，不是采样栅格。

### ③ 注入 100 ms 只测到 188 ms：定时器会提前触发

修好 ② 之后发现新问题：100 ms 单向注入，往返只测得 187.8 ms（理论 200 ms）。
用一个带真实时钟的探针测每段调度误差：**p50 = −6.00 ms，min = −7.00 ms** ——
`call_later` 系统性地**提前**约 6 ms 触发。

根因还是 `loop.time()` 的粒度：目标时刻是用一个「最多落后 15.6 ms」的时钟算出来的。

处理：延迟注入改由独立线程用 `time.perf_counter()` 排程，到点后 `call_soon_threadsafe`
交回事件循环发送（`teleoplab/scheduler.py`）。线程等待只会偏晚，不会偏早。
往返恢复到 **203.8 ms**，画面 **110.0 ms**，与注入值一致。

> 教训：**先证明测量工具没坏，再去测别人。** 如果没做这三步，后面所有「弱网下延迟多少」
> 的结论都会建立在一个偏早 6 ms 的注入器上。

### ④ 跨机器模式：注入 50 ms 却测出 111 ms，代理进程忘了提高定时器分辨率

把链路拆成三个进程后第一次测：注入 50 ms 单向（往返理论 100 ms），
实测 **p50 = 110.98 ms，抖动 3.46 ms**，而最小 RTT 是 100.6 ms —— 说明基准路径是准的，
多出来的 ~10 ms 只在部分样本上出现。

原因：`high_resolution_timer()`（`timeBeginPeriod(1)`）只在 robot 与 operator 进程里调用过，
**代理进程漏了**。代理的延迟注入由独立线程排程，进程仍停留在 Windows 默认 15.6 ms
定时器粒度，于是 50 ms 的注入被量化成 60 多毫秒。

处理：`run_proxy()` 同样包一层 `high_resolution_timer()`。复测：

| | 修复前 | 修复后 |
|---|---|---|
| 指令往返 p50 | 110.98 ms | **101.88 ms** |
| 抖动 | 3.46 ms | **0.70 ms** |

> 这是第三次栽在同一件事上：**定时器分辨率是每个进程各自的事，漏一个进程就污染整条链路。**

## 降级策略

| 等级 | 帧率 | 分辨率 | 下行码率（实测） | 用途 |
|---|---|---|---|---|
| L0 | 20 fps | 64×48 | 496 kbps | 正常 |
| L1 | 10 fps | 32×24 | 约 30 kbps | 延迟/丢包升高 |
| L2 | 5 fps | 16×12 | 约 8 kbps | 保命，只留「看得见」 |

触发：窗口内 p95 指令年龄 > 250 ms → 立即降一档。
恢复：p95 连续 3 个窗口 < 200 ms → 升一档。

**为什么恢复要回滞**：如果 250 ms 降、249 ms 升，链路会在阈值附近反复切换，
操作员看到的抖动比不降级还糟。坏了先保命，好了再慢慢恢复。

## 已知局限

- **降级不降低延迟**。本模型里延迟是人为固定注入的，与带宽无关；真实弱网里两者耦合，
  要看到降级收益需要带宽受限模型。这一条不是 bug，是这次实验的结论。
- **没有编解码**。v0.1 传原始像素，所以「画面 p95」不含编码/解码开销；H.264 路径是下一步。
- **单机回环仍是默认路径**。`suite` / `run` 仍是单机回环；跨机器要用 `serve` 的三个角色，
  且只在同一台机器的两个进程上验证过（LAN 地址），**真实双机 / Wi-Fi 尚未实测**。
- **基线与抖动不可跨机器比较**。0.4 ms 基线与 3 ms 抖动都是本机调度噪声量级，换机器可能差 2×；
  跨机器只有「注入值 → 实测值」的相对关系和码率可比（见上面「跨机器复现」一节）。
- **Windows 定时器限制**。100 Hz 物理步长在 Windows 上实际约 60–65 Hz（帧率由累计 dt 控制，
  不受影响，但状态流的真实周期偏长）。
- **丢帧率样本量小**。6 秒 × 20 fps 只有 120 帧，10% 丢包的估计误差约 ±5 个百分点。
